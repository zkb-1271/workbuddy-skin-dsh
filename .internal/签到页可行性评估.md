# 签到页可行性评估（2026-11-05）

给 dsh 皮肤的自建设置页加一个「签到」页，把 WB-Checkin 那个 App 的签到能力搬进来。

## 结论

**UI 侧几乎零阻力，数据侧要选路线。** 设置页是纯注入 JS，没有构建步骤，
加一页 = 加一个 NAV 项 + 一个 `panelCheckin()` + 在 PAGES 表里注册一行。

真正的约束只有一个：**渲染进程是 `file://`，跨域调不到 `www.workbuddy.cn` 的接口**，
所以所有 HTTP 必须在 `workbuddy.cn` 同源上下文里发起。

## 现有机制（已确认）

| 环节 | 实现 |
| --- | --- |
| 注入 | `tools/apply.sh` → CDP（127.0.0.1:9222）按序 `run` 各模块；主窗口 `CDP_APP=main`，原生设置窗 `CDP_APP=settings` |
| 设置页 | `skin/settings2.js`：`NAV` 数组（19 项）+ 每页一个 `panelXxx()` + `PAGES` 表（`credits: panelCredits` 那一行，约 555 行）注册 |
| 积分数据 | `skin/credits.js` 建隐藏 iframe（`/profile/credits-usage`，workbuddy.cn 同源）→ 守护进程 `tools/credits.mjs` 每 60s 经 CDP 挂进该 iframe 调接口 → 写 `window.__wbdsCreditsData` + `localStorage['wbds.credits.cache']` → 页面每 1.5s 轮询渲染 |
| 动作 | 目前没有「按钮 → 守护进程」通道，页面上的按钮只做本地状态或跳原生 |

## 三种数据路线

### A. 只读展示 + 守护进程定时兜底签到（推荐）

- 守护进程每 60s 用 `~/.wb-checkin/accounts.json` 里的 Bearer token 逐号查状态，未签就签
- 结果写 `window.__wbdsCheckinData = { accounts: [{nick, uid, checkedIn, credits, lastAt}], ts }`
- 页面纯展示：两号状态、今日是否已签、下次兜底时间
- **优点**：不动网络暴露面、不需要按钮通道、和现有 credits 链路同构，最省事
- **代价**：页面上的「立即签到」按不动（只能等下一轮，≤60s）

### B. A + 本地回环端口做即时动作

- 守护进程顺带起 `127.0.0.1:<port>`，只收 `POST /checkin`，校验 `Origin` 为空、限本机
- 页面按钮 fetch 它 → 立刻签 → 回写结果
- **优点**：按了就走；两个号都能签（token 在守护进程手里）
- **代价**：多一个监听端口（虽然只回环），跟你现在「零端口注入」的洁癖有冲突

### C. 借 localStorage 当信箱

- 按钮写 `localStorage['wbds.checkin.req'] = Date.now()`；守护进程把轮询间隔降到 2s，读到就执行
- **优点**：零端口、零新依赖
- **代价**：延迟 2~5s，且日志里要能看出是哪个号、哪次请求（重入判断）

## 账号覆盖范围（关键差异）

- **当前登录的号**（`08a4820d`，WorkBuddy 正在用的）：iframe 里有 cookie，同源 fetch 直接能签，
  甚至不需要 token 文件
- **另一个号**（`楷.` / `54312a3e`）：WorkBuddy 里没有它的 cookie，只能用
  `~/.wb-checkin/accounts.json` 的 Bearer token → **必须守护进程读文件**，渲染进程读不到本地文件

所以「两个号都能签」这件事，天然要求走守护进程（A/B/C 都行），纯前端方案只能覆盖一个号。

## 接口（已实测可用，详见 `~/Projects/wb-checkin/.internal/接口笔记.md`）

- `POST /v2/billing/meter/checkin-activity-status` → `data.today_checked_in`
- `POST /v2/billing/meter/daily-checkin` → 幂等，返回「已签到」视为成功

## 风险

1. **接口非公开**：作者逆向所得，官方改字段就失效，得跟着修
2. **token 轮换**：refresh 是轮换制，并发刷同一个号必得 `12153`；守护进程里必须串行，
   且刷完要写回 `accounts.json`，否则会把 App 那边也搞失效
3. **双向写权限**：守护进程改 `accounts.json` 时最好加文件锁，避免和 App 同时写
4. **版本漂移**：皮肤依赖 5.9.3 的 DOM/接口，客户端升级后要复验
5. **不碰充值/订阅接口**：只做签到、待体验领奖、只读积分，和现有 README 的承诺一致
